# 공동 집필을 위한 글쓰기 기준

이 문서는 『The State of Vibe Coding』의 학생 저자와 집필을 돕는 AI가 함께 참고하는 기준이다. 한국어와 영어 원고에 공통으로 적용한다.

학생마다 가진 경험, 사례, 관점은 살린다. 독자가 장을 옮겨 읽어도 설명 수준, 용어, 근거 제시 방식은 일관되게 유지한다.

## 적용 시점

1차 초안 PR에서는 사실과 근거, 출처 표기, 변동 정보의 확인 날짜와 버전, 실행 결과, 아래 문장부호 규칙과 저자 확인을 필수로 점검한다. 설명을 더 읽기 쉽게 만드는 제안은 필수 수정과 구분한다. 꼭지마다 소제목과 문단 구조를 동일하게 맞추지 않는다.

저자는 초안 PR을 제출하기 전에도 [AI 문체 점검 목록](AI_PROSE_CHECKLIST.md)을 참고해 자기 원고를 점검한다. 문장 패턴, 어휘와 서식에 관한 항목은 문맥에 맞게 적용하며, 단어 목록이나 AI의 판단만으로 원고를 일괄 고치지 않는다. 초안이 모이고 장의 내용과 연결을 정리한 뒤에는 이 목록을 장 단위 문체 편집에도 참고한다. 각 단계에서 저자의 의미와 목소리를 보존한다.

## 1. 사람과 AI가 모두 이해할 수 있게 쓴다

사람에게는 개념을 이해하고 판단할 수 있는 설명을 제공한다. AI가 참고할 때는 적용 대상, 조건, 절차, 완료 기준을 파악할 수 있게 쓴다.

- 특정 제품을 사용해 본 경험을 전제하지 않는다.
- 전문용어는 처음 등장할 때 설명한다.
- “적절하게”, “잘”, “충분히” 같은 표현은 판단 기준을 덧붙인다.
- 예시는 예시라고 표시하고, 실제 관찰 결과와 구분한다.
- 앞 절을 읽어야 이해할 수 있다면 해당 절을 연결한다.

**모호한 표현**

> AI에게 충분한 컨텍스트를 제공해야 한다.

**구체화한 표현**

> AI에게 수정을 요청할 때는 수정할 파일, 현재 동작, 원하는 동작, 변경하면 안 되는 범위를 함께 전달한다. 오류를 고치는 작업이라면 오류 메시지와 재현 방법도 제공한다.

두 번째 문장은 사람이 준비할 정보를 알려주고, AI가 어떤 정보를 확인해야 하는지도 드러낸다.

## 2. 담백하고 직접적으로 쓴다

한국어 본문은 ‘~다’, ‘~이다’로 통일한다. 영어 본문은 직접적인 평서문을 기본으로 쓰고, 행동 주체가 중요하면 명시한다.

과장, 홍보 문구, 불필요한 감탄을 줄인다. 비유를 사용했다면 실제로 무엇을 뜻하는지 설명한다. 수사적 대구를 반복하지 않는다.

본문에는 다음 문장부호 규칙을 적용한다. 원문을 그대로 옮긴 직접 인용은 원문 표기를 보존한다. 코드, URL, 수식과 식별자는 문장부호 정리 때문에 내용을 바꾸지 않는다.

- 긴 대시(em dash, U+2014)는 쓰지 않는다. 문장을 나누거나 쉼표, 콜론, 괄호를 사용한다.
- 가운뎃점(U+00B7)은 쓰지 않는다. 문맥에 맞게 조사, 접속 표현, 쉼표로 풀어 쓴다.
- en dash(U+2013)는 숫자 범위에만 사용한다.
- 본문에 이모지를 넣지 않는다.

**수정 전**

> 컨텍스트 엔지니어링은 AI의 무한한 잠재력을 깨우는 혁신적인 패러다임이다.

**수정 후**

> 이 절에서 컨텍스트 엔지니어링은 AI가 작업에 참고할 정보를 선택하고 구성하는 작업을 뜻한다. 예를 들어 오류 수정을 요청할 때 관련 코드, 오류 메시지, 재현 절차를 함께 제공할 수 있다.

**Before**

> Context engineering unlocks the full potential of AI and takes development to the next level.

**After**

> In this section, context engineering means selecting and organizing the information an AI system uses for a task. For a bug fix, this information may include relevant code, the error message, and steps to reproduce the problem.

국문과 영문 모두 구체적인 설명을 제공하되, 각 언어에서 자연스러운 문장을 쓴다.

## 3. 용어와 설명의 범위를 맞춘다

책의 개념 사전에 있는 표기를 우선한다. 같은 개념을 특별한 이유 없이 다른 이름으로 바꾸지 않는다.

한국어에서는 필요한 경우 처음 등장할 때 영문을 병기한다.

> 컨텍스트 엔지니어링(context engineering)

같은 용어에 여러 정의가 있다면 차이를 설명하고, 해당 절에서 사용할 의미를 밝힌다. 저자의 구분이나 해석은 그 사실을 표시한다.

**수정 전**

> 바이브 코딩이란 AI를 이용해 개발하는 것이다.

**수정 후**

> 이 절에서는 바이브 코딩을 자연어로 AI에 요구사항을 전달하고, 결과를 확인하며 소프트웨어를 만드는 방식이라는 넓은 의미로 사용한다. 생성된 코드를 직접 읽지 않는 작업 방식으로 뜻을 한정하는 용례는 별도로 구분한다.

정의의 출처와 용례는 원문 자료를 확인해 연결한다.

## 4. 설명의 흐름을 만든다

꼭지를 작성할 때 다음 질문에 답할 수 있는지 확인한다.

1. 이 절은 어떤 문제나 질문을 다루는가?
2. 핵심 개념은 무엇인가?
3. 구체적인 사례에서 어떻게 나타나는가?
4. 어떤 조건에서 적용할 수 있으며, 한계는 무엇인가?

이 질문들을 모든 절의 소제목으로 반복할 필요는 없다. 역사, 개념 설명, 실습, 전망에 맞게 구성을 선택한다.

설명은 연결된 문단으로 쓴다. 목록은 단계나 병렬 항목에, 표는 같은 기준으로 여러 대상을 비교할 때 사용한다.

## 5. 조언에는 적용 방법과 확인 기준을 붙인다

“요구사항을 명확히 하라”, “작업을 작게 나누라”는 조언에는 독자가 따라 할 수 있는 사례를 붙인다.

**추상적인 조언**

> AI에게 요구사항을 명확하게 전달하고 결과를 검증하라.

**설명을 보완한 예시**

> 요구사항에는 입력, 출력, 예외 처리, 완료 기준을 적는다. 다음은 월별 매출 합계를 계산하는 작업에 대한 요청 예시다.

```text
입력: sales.csv
필수 열: month, amount
month 형식: YYYY-MM
amount 단위: 원, 숫자

작업:
- 같은 월의 amount를 합산한다.
- 결과를 월 오름차순으로 출력한다.
- 필수 열이 없거나 month 또는 amount가 비어 있으면,
  해당 문제를 알리고 계산을 중단한다.

완료 기준:
- 2026-01의 금액이 100과 200인 두 행을 입력하면,
  해당 월의 합계로 300을 출력한다.
```

> 작성한 프로그램에는 정상 입력과 오류 입력을 각각 넣어 본다. 위 요청의 완료 기준과 실제 출력이 일치하는지 확인한다.

이 예시는 가상의 요구사항이다. 실행해 본 결과처럼 서술하지 않는다.

## 6. 사실, 경험, 해석을 구분한다

날짜, 수치, 인용, 제품 기능, 연구 결과는 확인한 출처를 연결한다. 공식 문서, 원 논문, 원 발언 등 1차 출처를 우선한다.

### 출처 표기

출처는 해당 주장의 가까운 곳에 Markdown 링크로 적는다. 링크 제목은 「저자 또는 기관, 문서 제목」으로 통일한다. 저자, 기관이나 제목을 확인하지 못했으면 추정해서 채우지 않는다. 직접 인용은 따옴표나 인용 블록으로 구분하고, 긴 문서라면 페이지 또는 절도 적는다. 문서의 게시일이나 수정일은 확인되는 경우 함께 적는다.

다음은 표기 형식이다. 대괄호와 괄호 안의 설명은 실제 자료 정보로 바꾼다.

```text
[저자 또는 기관, 문서 제목](원문 URL) (게시 또는 수정: YYYY-MM-DD; 필요 시 페이지 또는 절)
```

### 바뀔 수 있는 정보

기능, 가격, 사용량 제한, 모델 성능과 도구 지원 여부에는 출처와 함께 확인 날짜를 `YYYY-MM-DD`로 적는다. 제품 또는 모델 이름과 버전을 기록하며, 버전이 공개되지 않는 서비스는 그 사실을 적는다. 확인 날짜를 해당 기능의 출시일처럼 쓰지 않는다.

가격에는 해당 요금제, 통화와 과금 단위를 적고, 지역이나 결제 주기에 따라 달라지는 조건도 함께 적는다. 실험 결과에는 모델과 도구 버전, 실행 환경, 비교 조건을 남긴다. 확인하지 않은 날짜나 버전을 만들어 넣지 않는다.

```text
[기관, 가격 안내](공식 원문 URL)
(확인: YYYY-MM-DD; 제품 또는 모델: 이름; 버전: 확인한 버전 또는 버전 미공개;
 요금제: 이름; 통화와 과금 단위: 실제 조건)
```

직접 해 본 결과에는 독자가 범위를 판단할 수 있는 조건을 적는다. 한 번의 경험을 모든 작업에 적용되는 결론으로 확대하지 않는다.

**근거가 부족한 표현**

> AI를 사용하면 개발 시간이 절반으로 줄어든다.

**측정 결과가 없을 때**

> 이 절에서는 AI를 사용한 개발 과정을 예시로 설명한다. 작업 시간의 변화는 측정하지 않았으므로 생산성 향상 정도를 판단할 수 없다.

**직접 측정했다면 기록할 내용**

- 수행한 작업과 완료 기준
- 사용한 도구와 버전, 측정 시점
- 비교 조건과 반복 횟수
- 측정 결과와 해석의 한계

코드와 명령은 실행해 보고 싣는다. AI가 “실행했다”고 작성한 문장은 실행 기록을 확인한 뒤 사용한다. 확인하지 못한 내용은 집필 중 표시해 두고, 제출 전에 검증하거나 삭제한다.

## 7. 국문과 영문에서 의미를 유지한다

두 언어에서 주장, 조건, 예시, 수치, 불확실성의 수준을 유지한다. 문장 구조와 어순은 각 언어에 맞게 조정한다.

**한국어**

> 이 방법은 관련 파일을 미리 식별할 수 있을 때 유용할 수 있다.

**의미를 유지한 영어**

> This approach may be useful when the relevant files can be identified in advance.

이를 “This approach improves coding accuracy”로 바꾸면 조건과 불확실성이 사라지고, 원문에 없는 효과가 추가된다.

원문 언어와 번역 파일의 수정 방법은 저장소의 언어 정책을 따른다.

## 8. AI와 집필할 때

원고를 작성하거나 수정하는 AI에 이 문서를 함께 제공한다. 예를 들어 다음과 같이 요청할 수 있다.

```text
첨부한 docs/WRITING_STYLE.md를 기준으로 다음 원고를 검토해 줘.

1. 원고의 주장과 저자의 관점을 유지한다.
2. 모호한 용어, 설명이 빠진 단계, 일관되지 않은 표기를 찾는다.
3. 추상적인 조언에는 구체적인 예시를 제안한다.
4. 확인하지 않은 사실, 출처, 실행 결과를 만들어 넣지 않는다.
5. 근거가 필요한 부분은 [출처 확인 필요]로 표시한다.
6. 저자의 판단이 필요한 부분은 [저자 확인 필요]로 표시한다.
7. 수정한 원고와 주요 수정 이유를 제시한다.
```

표시는 집필 중 확인을 돕기 위한 것이다. 제출 전에 저자가 해결한다. AI가 고친 문장과 제안한 예시도 저자가 전문을 읽고 검토한다.

## 9. 검토 단계와 저자 확인

PR 리뷰의 각 의견에는 다음 중 해당하는 구분을 붙인다.

- `[필수 수정]`: 사실 오류, 핵심 주장에 필요한 근거 부족, 잘못된 실행 결과, 변동 정보의 확인 날짜나 버전 누락, 필수 문장부호 규칙 위반, 빌드 오류 등이다. 해결한 뒤 병합한다.
- `[문체 제안]`: 반복 표현, 제목, 문장 길이, 강조 방식 등이다. 수정 이유를 제시하고 저자가 판단하도록 한다. 이런 제안만을 이유로 초안 진행을 막지 않는다.
- `[저자 확인 필요]`: 수정으로 주장, 해석, 결론이나 적용 범위가 달라지는 경우다. 해당 저자가 변경 내용에 명시적으로 답한 뒤 반영한다. 필수 수정 의견과 함께 표시할 수 있다.

교차리뷰에서는 다른 장과 겹치는 정의나 사례, 빠진 연결도 기록한다. 장 단위 편집에서는 조장이 각 꼭지의 주장을 종합해 흐름을 점검하고, 중복과 상호참조에 대한 수정안을 정리한다. 정의는 개념 사전의 설명과 맞추고, 각 꼭지에 필요한 맥락은 남긴다.

내용과 연결을 정리한 뒤 장 단위로 문체를 다듬는다. 이때 [AI 문체 점검 목록](AI_PROSE_CHECKLIST.md)을 참고해 반복되는 대구, 모호한 출처, 동의어 돌려쓰기, 예고 문장, 상투적인 결론, 채팅 흔적과 과도한 서식을 살핀다. 실제 조건을 설명하는 문장이나 필요한 불확실성 표현은 보존한다. 이 단계에서 고친 문장도 저자가 확인한다.

## 제출 전 확인

- [ ] 처음 등장하는 핵심 용어를 설명했다.
- [ ] 주요 조언에 적용 조건이나 구체적인 예시가 있다.
- [ ] 사실, 직접 경험, 해석을 구분했다.
- [ ] 출처와 실행 결과를 직접 확인했다.
- [ ] 변동 정보의 출처, 확인 날짜와 버전을 기록했다.
- [ ] 직접 인용을 제외한 본문의 문장부호 규칙을 확인했다.
